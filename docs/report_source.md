## 一、实验目的

本次 Python 程序设计课程大作业以"完整可运行的软件作品"为目标，选择**地下城探险 Roguelike（回合制地牢探险游戏）**作为题目，希望在一次完整的工程实践中达成以下四个目的。

**第一，把课堂上的语法知识串成一条完整的工程链路。** 课程中分别学习过变量与流程控制、函数与模块、面向对象、文件读写、异常处理、常用标准库与第三方库，但单点练习很难体会它们之间的配合关系。本次作业要求从零构建一个具备地图生成、回合制战斗、道具系统、存档读档、数据统计与图形界面的完整程序，正好把这些知识点放进同一条流水线里。

**第二，掌握"逻辑与界面分离"的工程方法。** 很多同学的项目把业务规则和界面代码混写在一起，导致程序既难以测试也难以修改。本次作业刻意把项目切成 `dungeon/`（纯逻辑层）与 `ui/`（表现层）两个包，并用一条自动化测试来保证这条约束不被破坏，目的是体会分层设计带来的可测试性与可维护性。

**第三，学会用数据验证自己的设计，而不是凭感觉调参数。** 游戏难度是否合理、一局要打多久、玩家最常死在哪一层，这些问题靠"自己玩两把"是答不上来的。本次作业实现了一个无界面的批量模拟器，用它跑几十局并生成图表，让数值平衡从"拍脑袋"变成"看数据"。

**第四，训练文档与规范意识。** 代码要有统一的命名、中文注释与类型注解；报告要讲清楚设计思路、画出流程图、给出测试证据。这些都是后续课程设计与毕业设计的基本功。

## 二、实验内容与任务描述

### 2.1 项目概述

本项目名为**地下城探险（Dungeon Delve）**，是一个运行在 Windows 桌面上的回合制 Roguelike 游戏。玩家扮演一名冒险者，从地下城第 1 层出发，逐层向下探索，最终在第 10 层击败 BOSS"深渊领主"完成通关。每局的地图、怪物、道具都由随机种子程序化生成，因此每一局的体验都不相同。

程序完全使用 Python 实现，界面基于标准库 `tkinter`，**不依赖任何外部图片素材**——地图上的石墙、地面、门、楼梯、角色与怪物全部由 Canvas 图元现场绘制，因此把项目复制到任何一台装有 Python 的电脑上都能直接运行。

### 2.2 核心玩法

| 要素 | 设计说明 |
|---|---|
| 地图 | 40 × 25 格的网格地牢，由 7~12 个随机房间与 L 型走廊连通，每格 24 像素 |
| 探索 | 半径 7 格的视野，采用 Bresenham 射线判断遮挡；走过但当前不可见的区域会整体压暗，未去过的区域全黑 |
| 战斗 | 撞向怪物即攻击，伤害 = max(1, 攻击 − 防御)，15% 概率暴击（×1.8），8% 概率落空 |
| 成长 | 击杀获得经验，升级提升生命上限、攻击与防御并回满血 |
| 道具 | 药水（回血）、武器（加攻）、护甲（加防）、卷轴（传送 / 烈焰 / 祝福）四类共 10 种 |
| 楼层 | 共 10 层，怪物生命每层 +16%、攻击每层 +22%；第 10 层为 BOSS 层，无下行楼梯 |
| 存档 | 3 个存档槽位，JSON 格式，支持原子写入、版本迁移与损坏自愈 |
| 统计 | 每局自动记录 14 项指标，可生成 5 张 matplotlib 图表 |

- 64 个单元测试在无显示器环境下 约 0.3 秒跑完；
- 批量模拟器可以在没有界面的服务器上跑上百局；

### 4.3 数据结构设计

**（1）实体继承体系。** `Entity` 是一个抽象基类，只负责"有坐标、有血量、能受伤"这些最基础的能力；`Player` 与 `Monster` 继承它并各自扩展。把 `take_damage` 与 `heal` 上提到基类，代码只写一次、两者共用，这也是"模块化设计、降低重复率"的直接体现。

```
Entity(ABC)
 ├── Player      等级 / 经验 / 金币 / 背包 / 装备 / 统计计数
 └── Monster     物种 / AI 类型 / 警戒半径 / 奖励经验与金币
```

道具使用独立的继承体系而不继承 `Entity`，因为道具不占据地图实体位，而是挂在地图的坐标字典上：

```
Item(ABC)
 ├── Potion    heal_amount
 ├── Weapon    atk_bonus
 ├── Armor     def_bonus
 └── Scroll    effect / power
```

**（2）地图表示。** 地图用两层的 `list[list[Tile]]` 存储，`Tile` 是 `IntEnum`（墙 0 / 地板 1 / 门 2 / 楼梯 3）。行优先的二维列表便于直接切成字符串存档：25 行 × 40 字符，体积约 1 KB，人眼可读、可 diff，比嵌套的 JSON 二维数组干净得多。

视野使用两个集合：`visible`（当前可见）与 `explored`（曾经看到过）。界面只读这两个集合决定格子的三种配色，不做任何遮挡计算。

**（3）回合状态。** `GameState` 持有随机源、玩家、地图、怪物列表、地面道具字典、楼层、回合数与状态标志，是本项目唯一的"可变状态中心"。它对外只暴露五个意图方法，内部则是一条固定的回合流水线：

```
玩家意图 → 玩家阶段 → 怪物阶段（逐个决策并结算） → 回合数 +1
        → 重算视野 → 判定死亡/通关/超时 → 推送表现事件
```

**（4）存档结构。** 存档是一个自描述的 JSON 对象，顶层字段包括 `version`（格式版本）、`meta`（摘要信息）、`rng`（种子与状态快照）、`player`、`dungeon`、`monsters`、`items`、`log` 与 `progress`。其中 `cls` 字段承担多态反序列化的分发键——读档时先用 `cls` 决定实例化哪个类，再按 `key` 从数据表重建数值，因此即使有人手工把存档里的 `heal_amount` 改成 9999，也无法造出作弊药水。

## 五、关键伪代码展示与说明

按照题目要求，本节只展示关键逻辑的伪代码，不直接粘贴实现代码。

### 5.1 地牢生成

```
算法 GenerateDungeon(层数 floor, 随机源 rng):
    建立 40 × 25 的网格，全部填为 WALL
    target ← min(7 + (floor − 1), 12)          // 房间数随层数增加，上限 12
    attempts ← 0
    while 房间数 < target 且 attempts < 240:
        w ← rng(4, 10);  h ← rng(4, 10)
        x ← rng(1, 宽 − w − 2);  y ← rng(1, 高 − h − 2)
        if 新房间与任一已有房间"外扩 1 格"后相交:
            attempts ← attempts + 1;  continue     // 重叠则重新随机
        把新房间加入房间列表
    for 每个房间 r:
        把 r 的内部全部挖成 FLOOR

    按房间中心的横坐标升序排序
    for 相邻的两个房间 (prev, cur):
        CarveCorridor(prev 中心, cur 中心)        // L 型：随机先横后竖或先竖后横

    for 每个房间的外框格:
        if 该格是 FLOOR: 改为 DOOR                // 走廊与房间交界处形成门

    // 楼梯放在 BFS 距离最远的可走格，保证玩家必须探索一段距离
    dist ← BFS(玩家出生点)
    楼梯位置 ← argmax(dist)
    在楼梯上写 STAIRS
```

这段伪代码对应两个设计取舍。其一是**链式连接**：把房间按中心横坐标排序后依次连接，只要房间数大于 1，整张地图必然连通，不需要额外做连通性检查（测试用 100 个随机种子验证了这一点）。其二是**楼梯取最远点**：如果楼梯随机放，玩家可能"出门就下一层"，整层地图形同虚设；取 BFS 最远点则强制玩家探索。

### 5.2 视野计算

```
算法 ComputeFOV(玩家坐标 (px, py), 半径 R = 7):
    清空 visible
    把 (px, py) 加入 visible，并加入 explored

    for dy from −R to R:
        for dx from −R to R:
            if dx² + dy² > R²:  continue                 // 只取圆形范围
            (x, y) ← (px + dx, py + dy)
            if 越界 或 (x, y) 就是玩家位置:  continue

            // Bresenham 连线：从玩家到目标格，逐格检查
            path ← Bresenham((px, py) → (x, y))
            blocked ← false
            for 除终点外的每一格 c in path:
                if c 是墙:  blocked ← true;  break

            if not blocked:
                visible ← visible ∪ {(x, y)}
                explored ← explored ∪ {(x, y)}
```

这里有一个容易被忽略的细节：判断遮挡时**只检查中间格、不检查终点**。这样墙本身是可见的（否则玩家看不到墙壁轮廓，地图会缺一圈），但墙后面的格子不可见，符合直觉。

半径取 7 时，每回合需要约 150 次连线判断，实测单帧耗时不足 1 毫秒，完全不影响手感。

### 5.3 战斗结算

```
函数 ResolveAttack(攻击方 atk, 防御方 defense, 随机源 rng):
    if rng.random() < 0.08:                 // 8% 落空
        return { hit: false, damage: 0 }

    damage ← max(1, atk − defense)          // 关键：伤害下限为 1
    crit ← (rng.random() < 0.15)            // 15% 暴击
    if crit:
        damage ← round(damage × 1.8)

    return { hit: true, crit: crit, damage: damage }
```

`max(1, ...)` 这个下限是必须的。早期版本没有它，当玩家防御成长超过怪物攻击时，会出现"双方都只能造成 0 点伤害"的死循环，程序直接卡死。加上下限后最坏情况也只是"打得很慢"，不会卡住。

这个函数是**纯函数**：不修改任何对象、不读写全局变量、随机源由参数注入。因此测试可以传入一个"按脚本返回布尔值"的假随机源，把"落空""普通命中""暴击"三种情况都写成百分之百确定的断言。

### 5.4 存档读写与随机数恢复

```
函数 SaveGame(游戏状态 state, 槽位 slot):
    数据 ← state.ToDict()
    data["version"] ← 1
    data["rng"]["seed"]  ← state.rng.seed
    data["rng"]["state"] ← state.rng.GetState()      // 625 个整数的快照
    文本 ← JSON 序列化(数据, ensure_ascii = false, indent = 2)

    打开 "<slot>.json.tmp" 写入文本
    刷新缓冲区并 fsync 落盘
    os.replace("<slot>.json.tmp", "<slot>.json")     // 原子替换

函数 LoadGame(槽位 slot):
    if 文件不存在: 抛出 SaveError("该槽位是空的")
    try:
        数据 ← JSON 解析(读取文件)
    except JSON 解析失败:
        备份原文件为 "<slot>.json.bak"
        抛出 SaveError("存档已损坏，已备份为 .bak")

    if 数据.version > 当前版本: 抛出 SaveError("存档版本过新")
    while 数据.version < 当前版本:
        数据 ← MIGRATIONS[数据.version](数据)        // 迁移函数链
        数据.version ← 数据.version + 1

    恢复随机源：rng.set_seed(数据.rng.seed); rng.SetState(数据.rng.state)
    依次重建：玩家 → 地图 → 怪物 → 地面道具 → 进度与日志
    返回新的 GameState
```

存档设计有三个刻意为之的选择。

**其一是只存 JSON、不用 pickle。** pickle 在反序列化时会执行任意代码，存档一旦被替换或从网上下载，就相当于给电脑开了后门；而且 pickle 记录的是"模块路径 + 类名"，只要重命名一次类或调整一次目录，所有老存档立刻报废。JSON 只能构造数据、不能执行代码，字段是自描述的，加字段也不会让旧档报错。

**其二是同时保存种子与状态快照。** 只存 `seed` 只能"重放整局"，无法回到"当前这一刻"——因为 Mersenne Twister 已经抽取过几百次，状态早已不是初始状态。所以存档额外保存 `getstate()` 返回的 625 个整数。代价是每个存档多约 6 KB，换来的是**读档后怪物的每一次 AI 决策都与存档时完全一致**。这条性质由 `test_rng_state_reproducible` 守住：先存档、再取 10 个随机数、读档后再取 10 个，两次必须完全相同。

**其三是原子写入。** 先写临时文件、`fsync` 强制落盘、再用 `os.replace` 原子替换。这样即使写到一半断电或程序被强杀，旧存档也不会被写坏。

### 6.3 界面性能优化

一个容易被忽略但影响体验的问题是：如果每回合都 `delete("all")` 重画整张地图，1000 个格子会造成明显的输入延迟。本项目的做法是**启动时一次性创建全部 2002 个图元并缓存 item id**，之后每回合只对"外观签名"发生变化的格子调用 `itemconfig`。

实测一次移动通常只有 2 个格子（起点与终点）加上视野边缘的十几格需要更新，单帧更新量不到 50 次，从按键到画面刷新几乎无感。迷雾的三种状态通过**改同一个矩形的填充色**实现，不额外增加图层，因此也不会出现遮挡错位。

此外还做了三处细节优化：伤害飘字数量硬性限制为 20 个，超出时丢弃最旧的；飘字动画用 40 毫秒节流而不是每帧重绘；鼠标悬停只移动一个高亮矩形，不做任何重计算。

### 6.5 数值平衡的迭代过程

这套数值不是一次调好的，而是靠模拟器反复验证出来的。中间有三个值得记录的转折点：

**第一次（初版）** 的怪物攻击每层只增长 10%，而玩家防御每级 +1。模拟 30 局后发现所有对局都能轻松走到第 10 层，图表上是一条毫无起伏的直线——原因是玩家到 10 级时防御已达 13 点，而第 9 层的骷髅兵攻击只有 13 点，伤害被完全抵消。把怪物攻击成长提高到每层 22% 后，阵亡层数才分散到第 6~10 层。

**第二次** 发现自动玩家很少更换装备，导致中期战斗力严重不足。检查后发现这是模拟器本身的缺陷（真实玩家一定会换装备），补上"自动装备更优武器护甲"的逻辑后，平均到达层数从 8.5 提升到 9.5。

**第三次** 是 BOSS 战。最初的 BOSS 有 420 点生命、32 点攻击，模拟结果显示到达第 10 层的玩家全部阵亡。单独模拟一场"满血玩家 vs BOSS"的决斗，玩家在第 11 回合倒下时 BOSS 还剩 38 点血——差距不大但始终差一口气。最终做了两处调整：把 BOSS 降到 340 点生命、23 点攻击；同时在进入第 10 层时让玩家回满生命（剧情上解释为"在通往深渊的石阶上稍作休整"）。后者解决的是更根本的问题——原设计下玩家往往带着残血和空药水进场，BOSS 战变成了比谁先掉血的算术题，而不是一场公平的决斗。

调整前后的对比：通关率从 0% → 3.3% → 47.5%（不同随机种子批次有波动，稳定在 33%~48% 之间）。

### 6.6 可替换的图标资源

游戏内所有"物件"（玩家、怪物、道具、楼梯、门）的图标都支持换成自己的图片，**不需要改任何代码**。资源清单位于 `assets/icons.json`，每条记录只声明三件事：键名、中文名、图片相对路径。`ui/icons.py` 负责解析与校验，`ui/icon_set.py` 负责把 PNG 缩放到 24×24，并为迷雾区域生成压暗版本。

查找采用"三级回退"：某件道具先找 `item.<道具名>`，没有就用 `item.<类别>`（所有药水共用一张），再没有就用 `item`（所有道具共用一张），最后回退到字符绘制（`@`、`g`、`/`、`↓`）。因此只画一张图就能覆盖一整类物件，想给某一件单独做图再覆盖即可。替换后按 F12 即可热重载，不必重启程序。

实现上有三个细节值得记录。第一，`PhotoImage` 必须由图标集对象长期持有——Canvas 只记录 Tcl 侧的图像名字，Python 对象一旦被垃圾回收，Tcl 图像随之删除，画布上的格子会凭空消失。第二，生成迷雾变暗版时必须把 RGBA 拆开、只压 RGB 通道，因为 `Image.eval` 与 `ImageEnhance.Brightness` 都会连 alpha 一起压，半透明图标的边缘会糊成黑边。第三，热重载要按"先建新、再刷新、最后丢旧"的顺序，反过来会有一瞬间画布仍指着已释放的图像。

墙和地板**故意不做成图片**：它们承担着战争迷雾的三态显示，现在只改一个填充色就能完成；换成贴图后每层 1000 个格子都要切换图像，还要为迷雾再准备一套变暗版本，收益几乎为零。

|---|---|---|

### 7.4 异常处理策略

项目在四个层面做了分级容错：

| 层面 | 策略 |
|---|---|
| 底层逻辑 | 非法数值抛 `ValueError`（如负数伤害），越界坐标一律当作墙，道具使用失败返回 `(False, 原因)` 而不是抛异常 |
| 存档层 | 所有读写异常统一包装成 `SaveError`，消息用中文描述得能直接给用户看 |
| 界面层 | `try/except SaveError` 把错误转成弹窗；任何写操作失败都不会让窗口失去响应 |
| 入口层 | `main.py` 捕获顶层异常并打印完整堆栈，同时在控制台暂停，避免双击运行时窗口一闪而过看不到错误 |

## 八、实验总结

### 8.1 完成情况

本次大作业完成了一个 4748 行核心代码（另加 1482 行工具脚本与 926 行测试）的完整 Python 项目，实现了程序化地图生成、回合制战斗、道具与装备、多层探索、BOSS 战、JSON 存档、数据统计与图形界面等全部预定功能。64 个单元测试全部通过，40 局批量模拟验证了难度曲线的合理性，并生成了 3 张流程图、5 张统计图表与 7 张界面截图作为实验证据。

### 8.2 主要收获

**第一，真正理解了"分层"的价值。** 刚开始写的时候，我习惯性地在界面回调里直接写"如果这个格子有怪物就扣血"。直到要写单元测试时才发现，这样写根本没法测——每跑一次测试就要弹一个窗口出来。改成"界面只调用意图方法、逻辑层推送事件"之后，测试变成了一件轻松的事，64 个用例 约 0.3 秒跑完，而且能在没有显示器的环境里跑。这个转变是本次作业最大的收获。

**第二，学会用数据代替直觉。** 调整数值时我的直觉是"BOSS 有 420 点血应该挺有压迫感"，但模拟器告诉我玩家根本打不过；把血降到 340 之后通关率也只有 3.3%，直到单独模拟一场决斗、逐回合看血量变化，才定位到真正的问题是"玩家带着残血进场"而不是"BOSS 太强"。如果没有模拟器，这个问题大概只能靠反复手动试玩来发现。

**第三，踩了不少工程细节的坑。** 比如高分屏下 tkinter 默认不是 DPI 感知的，界面会被系统拉伸变糊，而且在截图时坐标会差 1.5 倍；比如 `random` 模块的全局状态会被任何第三方库污染，所以项目里所有随机都必须走同一个 `Rng` 实例；比如 tkinter 的 `Text` 控件如果每回合都重建内容会明显拖慢输入响应，改成用"上一条日志对象的身份"做游标增量追加之后才顺畅。这些都不是课本上会讲的，但确实是写出"能用的程序"和"好用的程序"之间的差距。

### 8.3 存在的不足与改进方向

1. **怪物 AI 比较简单。** 目前只有"追击 / 游荡 / 守卫"三种模式，追击采用贪心走位，遇到墙角容易卡住。后续可以加入 A* 寻路，或者让怪物学会"绕后""集火"等战术。
2. **地图类型单一。** 只有房间加走廊一种生成方式，缺少洞穴、水域、陷阱等要素。可以引入 BSP 或元胞自动机生成洞穴地形。
3. **没有音效与动画。** 目前只有伤害飘字，怪物移动是瞬移。可以用 `pygame.mixer` 加音效，或给移动加插值动画。
4. **统计维度还可以更丰富。** 现在只统计了每局的汇总数据，没有记录单场战斗的细节，因此无法分析"哪种怪物造成的伤害最多"这类问题。

### 8.4 结语

从一张空白的文件夹到一个能跑、能存、能看数据的完整游戏，这次大作业让我第一次完整体验了软件开发的流程：需求分析 → 设计 → 编码 → 测试 → 调优 → 文档。代码量不算大，但每一个模块都要想清楚"它该负责什么、不该负责什么"，这种边界意识可能比多写几百行代码更有价值。
